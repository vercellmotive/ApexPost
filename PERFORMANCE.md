# ApexPost performance evidence

All numbers here were measured, and each plan is saved in [`docs/plans`](docs/plans). Open a `.sqlplan` file in SSMS to see the plan.

## Test environment and data

| Item | Value |
|---|---|
| Server | SQL Server 2022 Developer (16.0.4305.5), compatibility level 160 |
| Host | Docker on an Apple Silicon Mac, running the x64 image under emulation, with about 3.8 GB of memory |
| Volume | 2,006 branches, 62,186 stock rows, 200,234 transactions, 200,565 lines, 50,078 shipments, 20,051 money orders (1,015 above 1,000) |
| Status mix | 190,224 Paid, 10,006 Voided, 4 Refunded |
| Generated by | `sql/performance/00_generate_volume.sql`: fictional data, stored in a throwaway database |

**How to read the numbers:** logical reads are the main evidence, because they stayed the same across all 5 runs of each query. CPU and elapsed times are medians of 5 runs and are only useful for comparison: emulation and the small server mean they don't predict production speed.

## W1: low-stock report, where the first index was wrong

My first design, `(BranchCode, QuantityOnHand) INCLUDE (Sku)`, reduced reads but was too costly. `QuantityOnHand` is a key column that changes on every sale, so the row has to move in the index. I measured a filtered alternative and replaced the original with it (migration `ReplaceLowStockIndexWithFiltered`, ADR-35).

| Measure | No index | Composite (first design) | Filtered (kept) |
|---|---|---|---|
| Reads, one branch | 106 | 3 | **2** |
| Reads, all branches | 1,030 | 348 | **13** |
| Bulk update of all 62,186 rows (median ms) | about 300 | about 1,800 | **about 380** |
| Index size | none | 12,944 KB | **104 KB** |
| Rows in the index | none | 62,186 | **1,939** |

**Index:** `IX_BranchStock_LowStock (BranchCode, Sku) INCLUDE (QuantityOnHand) WHERE [QuantityOnHand] <= 5`

**Why this design:** only the few rows at or below the threshold are in the index, so a typical sale that leaves stock above 5 doesn't touch it.

**Limitation I measured:** the filter is fixed at 5, the default `Inventory:LowStockThreshold`. `usp_LowStockReport` uses the index at a threshold of 5, with 15 reads across all branches. At a threshold of 20 it can't, and falls back to a scan of 1,032 reads. It still gives correct results, just more slowly. If the threshold is permanently raised, the filter needs a new migration.

Plans: [`W1-low-stock-before`](docs/plans/W1-low-stock-before.sqlplan), [`W1-low-stock-after`](docs/plans/W1-low-stock-after.sqlplan), [`P1-usp-low-stock-branch`](docs/plans/P1-usp-low-stock-branch.sqlplan), [`P2-usp-low-stock-all`](docs/plans/P2-usp-low-stock-all.sqlplan).

## W2: daily sales by branch and date

**Index:** `IX_CounterTransactions_Branch_Date (BranchCode, BusinessDate) INCLUDE (Status)`

**Why this order:** both columns are equality tests, and `BranchCode` first also serves "a branch's recent days". `Status` is included rather than keyed, because 95% of rows are `Paid` and it does little to narrow the search. Including it means no lookup is needed to filter.

| Measure | Before | After |
|---|---|---|
| Plan shape | Clustered scan of `PK_CounterTransactions`, nested loops into lines | Seek on the new index, nested loops into lines |
| Reads, `CounterTransactions` | 4,182 | 3 |
| Reads, `TransactionLines` | 437 | 437 |
| CPU (ms) | 32 | 3 |

**What's left:** the remaining 437 reads are per-line lookups, which are about 6 reads for each of the 71 matching sales. A covering index on `TransactionLines` could cut them, but every sale inserts into that table, so I didn't add one for a report that already reads 440 pages.

Through the real procedure, `usp_DailyBranchSales` takes 590 reads for one branch and 3,210 for every branch.

Plans: [`before`](docs/plans/W2-daily-sales-before.sqlplan), [`after`](docs/plans/W2-daily-sales-after.sqlplan), [`P3-usp-daily-sales`](docs/plans/P3-usp-daily-sales.sqlplan).

## W3: shipment search by zone and service level

**Indexes:** `IX_ShippingRates_Zone_Level (ZoneId, ServiceLevel)` and `IX_Shipments_Rate (ShippingRateId) INCLUDE (TransactionLineId)`

| Measure | Before | After |
|---|---|---|
| Plan shape | Seek on rates, hash join, clustered scan of 50,078 shipments | Seek on rates, nested loops, seek on shipments |
| Reads, `Shipments` | 698 | 24 |
| Reads, `ShippingRates` | 2 | 2 |
| CPU (ms) | 16 | 2 |

**Honest finding:** `IX_ShippingRates_Zone_Level` made no measurable difference, with 2 reads both ways, because the table has only 60 rows and `UQ_ShippingRates_Zone_Type_Level` already leads on `ZoneId`. All of the gain came from `IX_Shipments_Rate`. The rates index costs only 16 KB and rates rarely change, so it does little harm, but the evidence says it could be removed.

Plans: [`before`](docs/plans/W3-shipments-before.sqlplan), [`after`](docs/plans/W3-shipments-after.sqlplan).

## W4: money-order search for auditors

**Index:** `IX_MoneyOrders_HighValue (Amount) INCLUDE (Fee, TransactionLineId) WHERE [Amount] > 1000`

| Measure | Before | After |
|---|---|---|
| Plan shape | Clustered scan | Scan of the filtered index |
| Reads | 412 | 10 |
| CPU (ms) | 5 | 1 |

The "after" plan is still a scan, and that's the right plan: the index holds exactly the wanted 1,015 rows, so reading all of it is correct. The same limitation as W1 applies if the threshold is lowered below 1,000.

## Write overhead and storage

| Index | Size | Rows |
|---|---|---|
| `IX_BranchStock_LowStock` | 104 KB | 1,939 |
| `IX_CounterTransactions_Branch_Date` | 7,888 KB | 200,234 |
| `IX_ShippingRates_Zone_Level` | 16 KB | 60 |
| `IX_Shipments_Rate` | 2,192 KB | 50,078 |
| `IX_MoneyOrders_HighValue` | 680 KB | 1,015 |

| Write test (median of 5, rolled back) | Without workload indexes | With them |
|---|---|---|
| Update all 62,186 stock rows, composite design | about 317 ms | about 1,806 ms |
| Update all 62,186 stock rows, filtered design | about 317 ms | about 380 ms |
| Insert 5,000 high-value money orders | about 109 ms | about 138 ms |

A single-row sale update reported 0 ms in every case, which is below the timer's resolution, so I can't claim a difference for one row. The money-order test is the worst case, because every inserted row goes into the filtered index.

## Fixing a non-SARGable predicate

| Measure | `YEAR(BusinessDate) = 2026` | `BusinessDate >= '20260101' AND < '20270101'` |
|---|---|---|
| Plan shape | Seek on `BranchCode` only, then a date check on each of the branch's rows | Seek on both key columns |
| Reads | 249 | 108 |
| CPU (ms) | 10 | 4 |
| Rows returned | 20,888 | 20,888 |

Both plans show "Index Seek", so the plan shape alone hides the difference. Only `BranchCode` is seekable with `YEAR()`, so it reads all of the branch's dates. The application avoids the problem by design, because reports filter `BusinessDate` by exact date.

Plans: [`year-function`](docs/plans/S1-sargable-year-function.sqlplan), [`date-range`](docs/plans/S1-sargable-date-range.sqlplan).

## Estimated versus actual rows

I expected reusing a plan compiled for rare `Refunded` to hurt common `Paid`. **My first run didn't show that**: `Paid` got its own good plan. The saved plan contains a `Dispatcher` element, showing that SQL Server 2022's Parameter Sensitive Plan (PSP) optimization kept separate plans for each. I turned PSP off for the demo and restored it afterwards.

| Run | Estimated rows | Actual rows | Reads | CPU (ms) | Plan |
|---|---|---|---|---|---|
| `Refunded`, compiles the plan (PSP off) | 1 | 4 | 993 | 42 | Index scan plus lookups |
| `Paid`, **reuses that plan** (PSP off) | 1 | **190,224** | **571,653** | 1,258 | Index scan plus lookups |
| `Paid`, compiled for itself (PSP off) | 189,941 | 190,224 | 4,182 | 84 | Clustered scan |
| `Paid`, with PSP on | 189,941 | 190,224 | 4,182 | 82 | Clustered scan |

**Explanation:** this is parameter sensitivity. The optimizer sniffed `Refunded` and estimated about 1 row, so a key lookup per row looked cheap. Reusing that plan for `Paid` performed about 190,000 lookups, costing 137 times the reads. Statistics weren't the cause: they were current, with a `modification_counter` of 0.

**Conclusion:** on this server, PSP handled the problem automatically at compatibility level 160. It would return on a lower compatibility level, or where PSP doesn't apply. `OPTION (RECOMPILE)` in the two report procedures avoids it regardless.

**Also seen, not investigated:** W2's seek estimated 1 row against 71 actual. It didn't hurt the plan, so I left it, and I don't have a verified explanation.

Plans: [`refunded`](docs/plans/M2-psp-off-refunded-compiles.sqlplan), [`paid reusing`](docs/plans/M2-psp-off-paid-reuses.sqlplan), [`paid fresh`](docs/plans/M2-psp-off-paid-fresh.sqlplan), [`with PSP`](docs/plans/M1-mismatch-paid-reuses.sqlplan).

## Choosing OPTION (RECOMPILE)

`@BranchCode = NULL` means two different queries in one. Measured through `usp_LowStockReport`, one branch uses 86 reads and every branch uses 15, both with the filtered index, because each run gets a plan for its actual values.

| Option | Assessment |
|---|---|
| `OPTION (RECOMPILE)` (chosen) | A plan for the actual values, and it lets the filtered index match `@Threshold`. It costs a compile per run, fine for an occasional report. |
| Two procedures, or an `IF` calling each | Stable plans with no compiles, but more code to keep in step. Better at high call rates. |
| `OPTIMIZE FOR UNKNOWN` | One average plan that suits neither case, and it couldn't match the filtered index. |
| Dynamic SQL | Workable with `sp_executesql`, but harder to read and easy to get wrong. |

## Blocking demonstration

Two real sessions, using `sql/transactions/blocking_session_1_writer.sql` and `blocking_session_2_reader.sql`, while session 1 held an uncommitted update to one stock row.

**My first prediction was wrong.** I expected default `READ COMMITTED` to block, and it didn't: EF Core turned on `READ_COMMITTED_SNAPSHOT` when it created the database (`is_read_committed_snapshot_on = 1`).

| Reader | Result | Value |
|---|---|---|
| `READ COMMITTED` (snapshot) | No wait (0.3 s, mostly connection time) | 1, the last committed value |
| `READ UNCOMMITTED` | No wait | 2, a dirty read that was later rolled back |
| `READ COMMITTED` with `READCOMMITTEDLOCK` | **Blocked for 6.3 s** until the writer rolled back | 1 |

While blocked, `sys.dm_exec_requests` showed:

| session_id | blocking_session_id | wait_type | command |
|---|---|---|---|
| 52 | 51 | `LCK_M_S` | `SELECT` |

**What this means for the app:** report and screen reads don't wait for clerks' sales, and they never see uncommitted stock. Snapshot versions use `tempdb`, which is the cost of that benefit. Writers still block each other, which is why `rowversion` handles sales.

## Concurrency: selling the last units

Sending 20 simultaneous one-unit sales through the running app, against a product with 10 in stock:

| Round | Successful sales | 409 conflicts | Insufficient stock |
|---|---|---|---|
| 20 requests | 4 | 16 | 0 |
| 10 requests | 6 | 4 | 0 |
| 10 requests, twice | 0 | 0 | 20 |

Exactly 10 units were sold, and stock finished at 0. It never went negative, and every rejected sale saved nothing.

**Trade-off:** with `rowversion`, requests that lose the race get a 409 even when stock remains, as in the first round. That's safe and the brief allows it, but a busy product would see clerks retrying. A bounded automatic retry would be the next step if this proved common.

## How the design avoids deadlocks

- **Consistent order:** sales and `usp_AdjustStock` both touch `BranchStock` before anything else.
- **Short transactions:** optimistic concurrency holds no locks while a clerk works, and the courier rate call finishes before the save begins.
- **Automatic retry:** `EnableRetryOnFailure` retries deadlock error 1205.

No deadlocks appeared in these runs, but I didn't deliberately try to force one, so this is a design argument, not proof.

## Conclusions

1. **Measure before trusting an index.** My low-stock index looked right on paper, but it made bulk updates about 6× slower. The filtered replacement is better on every measure, and I wouldn't have found it from reads alone.
2. **Filtered indexes suit this workload.** Both are tiny and cut reads by 98–99%, because auditors and low-stock reports only want a small part of each table. The cost is a threshold fixed in the index.
3. **One index didn't earn its place.** `IX_ShippingRates_Zone_Level` gave no measurable gain on a 60-row table.
4. **The plan name isn't enough.** The `YEAR()` query was an "Index Seek" and still read more than twice as much.
5. **Two of my predictions were wrong** (blocking and plan reuse), and both had server features behind them: Read Committed Snapshot and PSP. Running it mattered.

**Limits of this evidence:** one small emulated server, one run of synthetic data with even date and branch spreads, and no sustained load test. Reads are reliable, while timings are only comparisons.

## Generated SQL

Captured from EF Core with `ToQueryString()`. To refresh it, set `APEXPOST_SQL_CAPTURE_PATH` and run the test `ReadQueries_TranslateToSqlWithoutTracking`.

### Low stock (screen and dashboard)

```sql
DECLARE @threshold int = 5;
DECLARE @code varchar(10) = 'B001';

SELECT [b].[BranchCode], [b].[Sku], [p].[Name], [b].[QuantityOnHand]
FROM [BranchStock] AS [b]
INNER JOIN [Products] AS [p] ON [b].[Sku] = [p].[Sku]
WHERE [b].[QuantityOnHand] <= @threshold AND [b].[BranchCode] = @code
ORDER BY [b].[BranchCode], [b].[QuantityOnHand]
```

### Shipping volume by zone and service level

```sql
DECLARE @code varchar(10) = 'B001';

SELECT [s0].[ZoneId], [s0].[ServiceLevel], COALESCE(SUM([t].[Quantity]), 0)
FROM [Shipments] AS [s]
INNER JOIN [TransactionLines] AS [t] ON [s].[TransactionLineId] = [t].[Id]
INNER JOIN [CounterTransactions] AS [c] ON [t].[TransactionId] = [c].[Id]
INNER JOIN [ShippingRates] AS [s0] ON [s].[ShippingRateId] = [s0].[Id]
WHERE [c].[Status] = 'Paid' AND [c].[BranchCode] = @code
GROUP BY [s0].[ZoneId], [s0].[ServiceLevel]
ORDER BY [s0].[ZoneId], [s0].[ServiceLevel]
```

### Money orders and identity checks per branch

```sql
SELECT [c].[BranchCode], [t].[LineType], COUNT(*)
FROM [TransactionLines] AS [t]
INNER JOIN [CounterTransactions] AS [c] ON [t].[TransactionId] = [c].[Id]
WHERE [t].[LineType] IN ('MoneyOrder', 'IdentityVerification')
GROUP BY [c].[BranchCode], [t].[LineType]
```

### Branch transactions screen

```sql
DECLARE @p int = 200;
DECLARE @code varchar(10) = 'B001';

SELECT TOP(@p) [c].[Id], [c].[OccurredAtUtc], [c].[CounterCode], [c].[ClerkStaffId], (
    SELECT COUNT(*)
    FROM [TransactionLines] AS [t]
    WHERE [c].[Id] = [t].[TransactionId]), COALESCE((
    SELECT COALESCE(SUM([t0].[LineTotal]), 0.0)
    FROM [TransactionLines] AS [t0]
    WHERE [c].[Id] = [t0].[TransactionId]), 0.0), (
    SELECT TOP(1) [p].[Method]
    FROM [Payments] AS [p]
    WHERE [c].[Id] = [p].[TransactionId] AND [p].[Kind] = 'Sale'), [c].[Status], [c].[VoidReason]
FROM [CounterTransactions] AS [c]
WHERE [c].[BranchCode] = @code
ORDER BY [c].[OccurredAtUtc] DESC
```
